# Требования к оформлению PR

**1.** Тесты
   - Тесты должны быть. Если их нет, то должна быть веская причина для отсутствия, указанная в описании PR.
   - Тесты должны исполняться на гитхабе, а не только существовать.
   - Если PR посвящен устранению ошибки, то тесты должны воспроизводить ее на целевой ветке.
   - Тесты должны покрывать все ситуации, работоспособность в которых требуется проверить.
   - Тесты должны быть добавлены в подходящий файл.
   - Каждый отдельный тест должен содержать комментарий, описывающий, что он проверяет.
   - Набор тестов в конце своей работы должен возвращать базу данных в исходное состояние, чтобы не влиять на остальные тесты.
   - Перед запуском набора тестов база данных должна приводиться в требуемое для этих тестов исходное состояние, например должны удаляться таблицы, которые могут остаться после неудачно завершившегося предыдущего запуска этих тестов. Такое удаление таблиц должно быть обернуто в `-- start_ignore` и `-- end_ignore`, так как таблицы могут или существовать, или отсутствовать.
   - Код новых тестов должен быть оформлен так же, как код уже имевшихся в файле, в который они добавлены.

**2.** Если в PR собственная разработка, то описание PR - это описание будущего коммита, который получится в целевой ветке после объединения коммитов PR.
   - Если PR посвящен устранению ошибки, то описание должно раскрывать, в чем состояла проблема, которую исправляет патч, в чем состоит идея предложенного в патче способа исправления проблемы и почему этот способ корректен. При чтении описания должно быть легко понятно, какое поведение является некорректным и было исправлено, а какое является правильным и сохранилось. Как вариант, можно использовать прошедшее и настоящее время для обозначения этого отличия.
   - Описание должно быть понятным без необходимости задавать уточняющие вопросы автору. В описании должны использоваться общепринятые словосочетания.
   - Описание должно быть достаточным для понимания патча, но не избыточно большим (не должно быть подробного описания очевидных вещей, понятных по коду).
   - Описание должно соответствовать заданию, а также текущей версии патча.
   - Описание должно быть выполнено на английском языке. Описание должно соответствовать правилам правописания и построения предложений в английском языке, в описании не должно быть опечаток. Для выявления опечаток можно использовать LibreOffice или любой другой редактор с проверкой правописания.
   - Заголовок должен быть в повелительном наклонении, например Fix, а не Fixed.
   - Описание должно быть выравнено на границу 80 символов. 
   - Если есть необходимость в описании PR размещать какие-то подробности, которые не должны попасть в описание итогового коммита, их следует отделить горизонтальной чертой.   
   - Описание не должно содержать ссылок на ресурсы, которых нет в открытом доступе.

**3.** Если PR создан для переноса готовых коммитов из другого проекта, то все коммиты PR попадут в целевую ветку по отдельности
   - Описание коммитов должно быть дополнено указанием, какой коммит был взят за основу
   - Если потребовались существенные изменения оригинального патча для его адаптации, их описание должно присутствовать в коммите. Пример дополнения к описанию:
```
(cherry picked from commit 0fda682)

Changes from original commit: remove API changes and Windows
compatibility code to keep binary compatibility with 6.x
```
   - Авторство должно быть сохранено

**4.** Код
   - Код должен соответствовать [требованиям к оформлению](codestyle_ru.md)
   - PR не должен содержать изменения, логически не связанные между собой. В противном случае следует разделить PR на несколько для упрощения ревью и облегчения возможного отката итогового коммита.
